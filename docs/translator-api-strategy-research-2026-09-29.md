# Translator API 활용·품질·사용자 경험 조사

조사일: 2026-09-29. 별도 조사 에이전트가 공식 문서·현행 사양·공개 구현 사례를 검토했다. 이 문서는 조사 산출물이며 코드 변경이나 실제 번역 벤치마크 결과가 아니다.

## 판단 요약

Translator API의 장점은 로컬 처리, 낮은 서버 운영비, 반복 사용 시 빠른 응답이다. 품질을 높이려면 원문의 의미를 가리는 전처리를 줄이고 완결된 문장과 관련 문맥을 유지해야 한다. 만족도를 높이려면 원문 확인, 진행 상태, 실패 복구, 사용자 선택을 제공해야 한다.

영어→한국어 등반 문서에서 이러한 전략으로 정확도나 만족도가 얼마나 개선되는지 입증한 공개 성과는 찾지 못했다. 아래에서 **확인된 사실**, **공개 사례**, **프로젝트 적용 가설**을 구분한다. 기존 원문 보기·복원·상태 표시·취소·캐시 기능은 먼저 확인하고 부족한 부분만 추가한다. 조사에 언급된 기존 문제는 앞선 진단을 기준으로 하며, 병행 작업의 최신 수정 상태를 반영한 코드 감사 결과가 아니다.

## 1. 기본 활용 전략

| 항목 | 확인된 동작 및 설계 방향 |
|---|---|
| 지원 범위 | Chrome 공식 문서는 데스크톱 지원, 모바일 미지원으로 안내한다. 버전 추측보다 `Translator` 존재와 언어쌍별 `availability()`를 검사한다. |
| 준비 상태 | `unavailable`, `downloadable`, `downloading`, `available`을 구분한다. API 미지원·언어쌍 미지원·최초 다운로드를 같은 실패로 표시하지 않는다. |
| 최초 실행 | 다운로드가 필요한 생성은 사용자 활성화가 필요하므로 번역 버튼의 클릭 흐름에서 시작한다. 다운로드 완료와 객체 준비 완료를 구분한다. |
| 언어 선택 | 영어임을 아는 본문은 `en→ko`로 지정한다. 언어가 불확실한 댓글 등만 감지하고 사용자가 원문 언어를 수정할 수 있게 한다. |
| 호출 위치 | 공식 웹 API는 Window 대상이며 Web Worker에서 사용 가능하다고 가정하지 않는다. 확장은 실제 실행 문맥과 권한을 확인한다. |
| 작업 순서 | Chrome은 번역 요청을 순차 처리한다고 안내한다. 현재 읽는 본문과 사용자 선택 요청을 우선하고 불필요한 작업을 취소한다. |
| 긴 입력 | 출력 스트리밍을 사용할 수 있지만 입력 스트리밍과는 다르다. 문장을 중간에서 잘라 연속 전송하는 방식은 피한다. |

근거: [Chrome Translator API](https://developer.chrome.com/docs/ai/translator-api), [공식 설계 설명](https://github.com/webmachinelearning/translation-api).

언어쌍별 객체를 재사용하고 더 이상 필요하지 않으면 `destroy()`로 해제한다. `AbortSignal`로 생성과 번역을 취소할 수 있다. 페이지 이동·원문 복원 뒤 이전 결과가 화면을 덮지 않도록 요청 세대 번호를 관리하는 것은 프로젝트 적용 제안이다. 현행 사양의 입력량 측정·한도 인터페이스는 실제 Chrome 지원을 기능 검사하며, 제한 초과 시 문장 경계 분할과 오류 처리를 준비한다. [현행 사양](https://webmachinelearning.github.io/translation-api/), [Chrome 운영·UX 권고](https://developer.chrome.com/docs/ai/built-in-ai-dos-donts?hl=en).

## 2. 품질 전략과 API 한계

| 전략 | 근거 수준 | 적용 방향 |
|---|---|---|
| 완결된 문장 유지 | 공식 설계 설명 | 링크·강조 태그 때문에 문장을 조각내지 않는다. |
| 인접 문단 묶기 | 검증할 가설 | 의미가 이어지는 문단에 한해 실험한다. 길수록 좋다고 가정하지 않는다. |
| 일반 용어 원문 유지 | 앞선 진단에 따른 적용 제안 | `anchor`, `belay`, `pitch`를 무의미한 토큰으로 가리는 처리를 줄인다. |
| 오역 사전 제거 | 앞선 진단의 명백한 수정 대상 | `route wanders → 불규칙한 앵커 루트` 같은 치환을 제거한다. 최신 변경 상태를 먼저 확인한다. |
| 필수 값 보호 | 구현·검증 필요 | 등급·장비 호수·거리·이름 등을 최소 보호하고 누락·중복·변조를 검사한다. |
| 문맥·용어집 옵션 | 현재 없음 | `context`, `sharedContext`, 프롬프트·말투·모델·온도 제어를 Translator 기능으로 가정하지 않는다. |
| HTML 처리 | 보존 계약 미확정 | 전체 HTML을 보내고 결과를 그대로 DOM에 넣는 방식을 채택하지 않는다. |

현행 `translate()` 옵션은 `signal`뿐이다. 객체 재사용이 이전 문장의 대화 문맥을 누적한다는 계약도 없다. 주변 문장을 입력에 추가하면 그것도 번역 대상이므로, 문맥만 보내고 목표 문단만 받으려면 별도 설계와 검증이 필요하다. [Translator 사양](https://webmachinelearning.github.io/translation-api/).

공식 설계는 문장 뒷부분에 따라 앞부분의 해석이 바뀔 수 있음을 설명한다. 이는 페이지 전체를 합치면 항상 좋아진다는 증거는 아니다. [설계 설명](https://github.com/webmachinelearning/translation-api).

HTML이 보존된 동작 사례는 있지만 입력 형식·속성 보존 등은 논의 중이다. 텍스트 추출과 DOM 복원을 분리하고 보호 항목 검증 실패 시 원문을 유지하는 것을 권한다. [입력 형식 논의](https://github.com/webmachinelearning/translation-api/issues/60), [현재 공개 이슈](https://github.com/webmachinelearning/translation-api/issues).

등반 용어는 본문을 강제로 치환하기보다 원어와 검수된 설명을 보여주는 보조 사전으로 분리할 수 있다. 이는 문장 생성을 방해하지 않으면서 이해를 돕는다는 가설이며 사용자 평가가 필요하다.

## 3. 공개 사례와 증거의 범위

| 사례 | 공개된 내용 | 가져올 전략과 한계 |
|---|---|---|
| Policybazaar | 다국어 상담과 영어→힌디어 기사 번역. 담당자가 1,000자 기사를 2초 이내 번역했다고 보고 | 필요한 순간 번역, 처리 중 표시, 낮은 지연. 해당 환경의 보고이며 한국어 성능 보장은 아니다. |
| JioHotstar | 부족한 자막 언어 보완을 탐색. 언어 선택 및 언어쌍별 객체 캐시 코드 공개 | 기존 자막 우선, 부족한 언어 보완, 객체 재사용. 전면 배포나 만족도 향상률로 해석하지 않는다. |
| Terra | 포르투갈어 기사→영어 요약→포르투갈어 결과를 CMS에 넣고 기자가 수정 | 검수와 편집, 실제 입력 반복 평가. Translator 단독 정확도 실험이 아니며 왕복 번역을 개선책으로 일반화하지 않는다. |
| Chrome Inline Translate | 선택 버블, 사이트별 목표 언어·일시중지. 드래그 중 번역을 선택 종료 후 실행으로 바꾼 개발 경험 | 읽던 위치 유지, 요청 절약, 선호 기억. 통제된 만족도 조사 없이 제작자 경험으로만 취급한다. |

출처: [Policybazaar·JioHotstar 공식 사례](https://developer.chrome.com/blog/pb-jiohotstar-translation-ai), [Terra 공식 사례](https://developer.chrome.com/blog/summarizer-terra-brightsites), [공개 확장 저장소](https://github.com/WINEEL/chrome-inline-translate).

공개 사례에서 확인한 것은 구현 방식과 일부 속도 보고다. 번역 정확도나 사용자 만족도가 특정 비율로 상승했다는 근거는 확보하지 못했다. 오래된 사례 코드는 현재 API 계약을 대신하는 구현 지침으로 복사하지 않는다.

## 4. 사용자 경험 적용 제안

아래 기능은 **이미 존재하는지 먼저 확인하고 부족한 것만 추가**한다.

1. 문단별 원문 보기·병기·전체 원문 복원으로 의미를 쉽게 대조한다.
2. 언어팩 다운로드·준비·번역 진행을 구분한다. 다운로드 퍼센트와 번역 진행률을 섞지 않는다.
3. 본문을 먼저 번역하고 댓글은 펼치거나 선택한 시점에 처리하는 방식을 검토한다.
4. 사이트별 자동 번역·표시 방식·목표 언어 선호를 기억한다.
5. 실패 문단은 원문을 유지하고 해당 문단만 재시도한다. 복원 뒤 늦은 결과가 다시 적용되지 않게 한다.
6. 의미 오류·어색함·용어·수치 오류 피드백을 해당 원문과 연결한다. 피드백이 자동으로 모델 학습에 반영된다고 표현하지 않는다.
7. 원문·언어쌍·전처리 정책 버전을 포함한 캐시로 지연을 줄인다. 정책 변경 시 무효화하고 새로 번역 기능을 제공한다.

되돌리기·진행 표시·사용자 통제·필요한 입력만 처리하기는 [Chrome 공식 UX 권고](https://developer.chrome.com/docs/ai/built-in-ai-dos-donts?hl=en)와 일치한다. 병기를 모든 사용자에게 강제할지는 별도 평가한다.

## 5. 대안 엔진·LLM

- **현재 API:** 로컬·오프라인 장점을 유지하며 확장 전처리로 생긴 손실을 먼저 제거한다.
- **다른 번역 API:** DeepL은 별도 문맥·용어집·태그 처리 옵션을 제공한다. 지원 언어·기능 조합을 확인해야 하며 인증·사용량 비용·외부 전송이 생긴다. 한국어 등반 문서의 우월성을 뜻하지 않는다. [DeepL 공식 문서](https://developers.deepl.com/api-reference/translate/request-translation).
- **LLM/Rewriter 후처리:** 유창해져도 의미 변경·정보 추가가 가능하므로 전체 자동 적용보다 선택 문단의 대안으로 실험한다. Rewriter의 문맥 옵션은 Translator 기능이 아니며 로컬 기반 모델의 지원·하드웨어 요구도 다르다. [Chrome Rewriter](https://developer.chrome.com/docs/ai/rewriter-api).

## 6. 이 프로젝트의 순서와 평가 계획

### 적용 순서

1. 최신 코드·병행 작업 상태를 확인하고 전처리 없는 API 기준선을 확보한다. 오역 사전·일반 용어 토큰화·필수 값 복원·캐시 정책을 점검한다.
2. 기존 원문 보기·복원·상태·취소·선택 번역을 확인하고 부족한 부분만 개선한다.
3. 인접 문단 묶기, 보조 용어 사전, 선택적 대안 엔진을 각각 독립 실험한다.

### 비교와 측정

같은 원문으로 현재 확장, 전처리 없는 API, 개선 확장, Chrome 메뉴 페이지 번역을 비교한다. 메뉴 번역과 API의 결과가 같다는 공개 계약은 확인되지 않았다. API 설계도 품질·안정성·브라우저 간 동일성을 보장하지 않는다. [공식 비목표](https://github.com/webmachinelearning/translation-api).

대표 원문 40~60개를 일반 설명·확보/하강·접근로·장비/등급·구어체 댓글·링크/목록으로 나누어 평가한다.

- 품질: 블라인드 의미 정확도·자연스러움·용어 적절성. 누락·추가·부정·방향·수치·위험 수준 변형을 별도 집계.
- 보존: 등급·호수·거리·이름·링크·서식 복원.
- 속도: 최초 다운로드와 준비 완료 후 지연을 분리. 첫 결과·전체 완료 p50/p95.
- 만족도: 이해도 질문 정답률·읽기 완료 시간·선호 번역·짧은 만족도 응답.
- 해석: 원문 보기 횟수만으로 불만족을 단정하지 않는다. 대조 확인과 학습 목적일 수 있다.

추천 채택 기준은 평가 자료에서 새 중대 의미 오류 0건, 필수 값·서식 보존 100%, 현행 대비 의미 정확도·자연스러움 개선이다. 이는 향후 검증 기준이며 현재 달성한 결과가 아니다.
